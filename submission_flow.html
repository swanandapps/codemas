Flow begins
1
Browser Student submits code

Student hits Submit. The browser POSTs the question ID, code and language, plus the behavioural signals used later by plagiarism scoring.

// ExamTakeView.vue — frontend const res = await api.post('/submissions/create/', { question: questionId, code: editorCode, language: 'python', // + had_paste_event, paste_char_count, tab_switch_count, … })
2
Django Validate input & fetch question

Django checks the question exists and validates the serializer fields. Nothing is written yet.

# submissions/views.py — SubmissionCreateView question = Question.objects.filter(pk=question_id).first() if not question: return Response({'error': 'Question not found'}, status=404) serializer = SubmissionCreateSerializer(data=request.data) if not serializer.is_valid(): return Response(serializer.errors, status=400)
3
Postgres One transaction: lock, count attempts, write submission + outbox job

The student's User row is locked. A second submit from the same student waits here until the first commits, then counts it: it becomes the next attempt, or gets 403 at the limit. Submissions that ended in error (a dead job, or a question with no tests) don't count against the limit. The submission and its job row are committed together or not at all. The request never touches a queue. C++ and Java skip the job row and go to the legacy Celery task after commit.

# submissions/views.py with transaction.atomic(): User.objects.select_for_update().get(pk=request.user.pk) mine = Submission.objects.filter(student=request.user, question=question) if mine.exclude(status='error').count() >= max_attempts: return Response({'error': 'Max attempts reached'}, status=403) attempt_number = (mine.aggregate(m=Max('attempt_number'))['m'] or 0) + 1 submission = serializer.save(..., attempt_number=attempt_number) if submission.language in settings.PIPELINE_LANGUAGES: # python, javascript enqueue(Job.KIND_EXECUTE, submission.id) # jobs_job row, status 'pending' else: transaction.on_commit(lambda: execute_submission.delay(submission.id)) # a concurrent submit waits on the lock above, then counts this one (next attempt, or 403 at the limit) # unique (student, question, attempt_number) is the backstop for writers outside the lock → 409
4
Browser Receive 201 — start polling the status endpoint

Django returns 201 at once. The browser polls /status/: immediately, then every 1 s for 5 polls, 2 s for 2, then every 3 s; after 2 minutes, every 10 s. The submission ID is kept per question in sessionStorage, so polling resumes after a refresh. The same endpoint serves the legacy Celery path ("job": null).

// ExamTakeView.vue const POLL_DELAYS_MS = [1000, 1000, 1000, 1000, 1000, 2000, 2000, 3000] const SLOW_POLL_AFTER_MS = 120000, SLOW_POLL_MS = 10000 const { data } = await api.get(`/submissions/${id}/status/`) // { id, status, results_ready, job: { status, attempt, queued_at, started_at, finished_at } }
Relay publishes the outbox
5
Relay Pick up pending jobs with SKIP LOCKED, publish, mark queued

Every 0.5 s the relay locks up to 50 pending jobs, oldest first. SKIP LOCKED lets several relays run without taking the same rows. A job becomes queued only if the transport accepted it; anything else stays pending, with the error in last_error, for the next tick. A crash between sending and marking can publish a job twice, which is harmless because claiming is idempotent.

# jobs/relay.py — tick() jobs = list(Job.objects.select_for_update(skip_locked=True) .filter(status='pending').order_by('created_at')[:50]) outcome = transport.publish_many(jobs) # {job_id: None | error} for job in jobs: if outcome.get(str(job.id)) is None: Job.objects.filter(pk=job.pk).update(status='queued', published_at=now) # once a minute: sweep_stuck() — requeue lost messages / expired leases, mark dead at 3 attempts
6
Transport sqs: send the job id to codemas-exec · local: hand it to a thread pool

The message is only the job id, the kind and a per-job token, HMAC-SHA256(JOB_SIGNING_SECRET, "job:" + job_id), minted by the relay. No code, no test answers, no secret. sqs sends 10 per send_message_batch call with short botocore timeouts, and SQS triggers the Lambda. local (built and used today) runs the real lambda/exec/handler.py in a thread pool inside the relay, and redelivers a failed delivery after 2 s and 5 s, like SQS would. An unknown JOB_TRANSPORT raises an error instead of falling back.

# jobs/transports.py body = {"job_id": "7f3c…", "kind": "execute_submission", "token": job_token(job.id)} # SqsTransport client.send_message_batch(QueueUrl=JOB_QUEUE_URL, Entries=[{ 'Id': job_id, 'MessageBody': json.dumps(body), 'MessageAttributes': {'job_id': …, 'language': …}}, …]) # ≤ 10 per call # LocalTransport.publish event = {'Records': [{'messageId': job_id, 'body': json.dumps(body)}]} self.pool.submit(self._deliver, event) # _deliver: handler.handler(event, None); if batchItemFailures, deliver again after 2 s, then 5 s
Executor (the same handler code locally and on Lambda)
7
Lambda Claim the job from Django (job token) — lease, token, payload

The handler holds no database credentials, no shared secret and no answers. It sends back the token from the message; Django recomputes it and answers 401 if it doesn't match (a token works only for its own job). One locked read decides the outcome: a finished job gets 409 done (acknowledged), a live lease gets 409 busy (retried later), a job already at 3 attempts becomes dead (410) and its submission error. Otherwise the job becomes running with a new token and a 150 s lease (longer than the 90 s function timeout), and attempt goes up by 1.

# lambda/exec/handler.py status, job = _post('/internal/jobs/claim/', {'job_id': job_id, 'token': token}) # no signature headers; Django: hmac.compare_digest(job_token(job_id), token) else 401 # Django → 200 { "lease_token": "c91e…", "submission_id": 42, "language": "python", "code": "...", "tests": [{ "id": 301, "input": "..." }, …], # no expected outputs: they never leave Django "limits": { "timeout_s": 10, "python_memory_mb": 256, "node_heap_mb": 192, "output_kb": 64 } }
8
Lambda Run each test in a sandboxed child process

Each test runs in a fresh child process with no shell, an empty environment, its own process group and rlimits. A 10 s wall-clock timeout kills the whole group, and output is capped at 64 KB. The Lambda holds no secret and no expected outputs for student code to find. Known limits, accepted: on real Lambda student code can reach the internet (Lambda refuses the seccomp filter) and can read the role's AWS credentials. On Lambda (or with CODEMAS_EXEC_SCRUB=1) the temp dir is wiped and leftover processes are killed between runs. After the first student timeout the remaining tests are marked "Not run". If the Lambda itself runs out of time first, or the grader throws, the handler calls /fail/: the job goes back to pending and the relay republishes it. That is never a failing grade.

# lambda/exec/sandbox.py — run() cmd = [sys.executable, '-I', 'main.py'] # or: node --max-old-space-size=192 main.js proc = subprocess.Popen(cmd, cwd=workdir, env={}, start_new_session=True, preexec_fn=_preexec(language, limits)) # _preexec: RLIMIT_CPU 10 s · RLIMIT_FSIZE 1 MB · RLIMIT_AS 256 MB (Python) · RLIMIT_NPROC 32 (Linux) proc.wait(timeout=10) # then os.killpg(pid, SIGKILL), always # handler.py — per test result sent back (Django decides pass/fail) { "test_id": 301, "output": "2", "error": "", "ms": 41, "timed_out": false }
9
Postgres Complete — Django grades and records, only if the token still owns the job

In one transaction Django checks the lease token, writes one Result row per test, sets the submission to passed or failed, and marks the job succeeded. The pass rule is the same as the legacy executor: output.strip() == expected.strip(). A stale token gets 409 and nothing is written. A question with no tests ends as error, never a pass. After commit, the same side effects as the legacy task run: normalise the code, notify, and queue the AI rubric and hint on Celery.

# jobs/services.py — complete() → jobs/execute.py — apply_result() job = Job.objects.select_for_update().get(pk=job_id) if job.status != 'running' or str(job.lease_token) != str(lease_token): raise StaleLease # → 409 Result.objects.update_or_create(submission=sub, test_case_id=r['test_id'], defaults={…}) sub.status = 'passed' if all_passed and not missing else 'failed' job.status = 'succeeded' transaction.on_commit(lambda: after_grading(sub.id), robust=True)
10
Browser Next poll sees passed / failed — fetch per-test results

The tracker moves Queue → Execute → Grade from the job status and never moves backwards. A retry shows "Retrying…"; a wait over 10 s shows "Taking longer than usual…". A dead job tells the student it couldn't be graded and doesn't count as an attempt.

// ExamTakeView.vue if (data.status === 'passed' || data.status === 'failed') { const res = await api.get(`/results/${submissionId}/`) // per-test breakdown } // job.status === 'dead' → "We couldn't grade this submission … doesn't count as an attempt"

When something goes wrong
SituationWhat happens
Relay downJobs wait as pending and publish on the first tick after restart.
Queue unreachablePublish fails; the job stays pending with publish failed: … in last_error and is retried every tick.
Grader error, or Lambda out of time before any student timeoutThe handler calls /fail/: the job goes back to pending (the attempt still counts) and the relay republishes it on the next tick. The message is acknowledged.
Crash or Lambda timeoutSQS: the message reappears after the 540 s visibility timeout (about 9 minutes) and the expired lease is reclaimed with a new token. Local: redelivery after 2 s and 5 s, then the sweep requeues the expired lease.
Duplicate deliveryThe second claim gets 409 done or busy. Only the lease holder can complete.
Three attempts usedThe job becomes dead and the submission error, which doesn't count against the student's attempts.
Wrong answer, error or student timeoutA normal succeeded job with a failing grade. Never retried.
codemas-exec-dlq holds messages whose delivery wasn't acknowledged 3 times. Causes: crashes and timeouts; Django unreachable; a claim refused with 401, 404 or busy; a failed /fail/ call; a complete answered with anything but 200 or 409; and claims skipped because less than 30 s of Lambda time was left. A job released through /fail/ has its message acknowledged, so it dies in Postgres with no DLQ message.

Table Connections
From Field To Type Pattern / Why
Question .exam → Exam N → 1 Normalization — many questions per exam; exam title lives in one row
TestCase .question → Question N → 1 Normalization — expected_output belongs to the question, not every result
ExamEnrollment .exam + .student → Exam + User Junction M:N resolved — student enrolls in many exams; exam has many students
Submission .student / .question → User + Question N → 1 Core FKs — submission always belongs to one student and one question
Submission .exam → Exam N → 1 Denormalization — also reachable via .question.exam, but stored here for direct one-table filtering
Result .submission → Submission 1 → N One submission runs against N test cases → N Result rows, one per test case
Result .test_case → TestCase N → 1 Normalization — actual_output goes on Result; expected_output stays on TestCase
BehaviouralFlag .submission → Submission 1 : 1 Extension — adds plagiarism data without polluting the core Submission table
PlagiarismFlag .submission_1 / ._2 → Submission × 2 N → 1 Cross-comparison — one row per similar pair; unique_together prevents duplicate pairs
PolicyVersion .changed_by → User N → 1 Audit trail — immutable before/after snapshots of every policy change
DisputeRequest .student / .resolved_by → User × 2 N → 1 Two FKs to same table — different roles (submitter vs resolver)
Design Patterns Used
Normalization
Exam → Question → TestCase
Each piece of data lives in exactly one place. TestCase.expected_output is never duplicated — update it once and every query sees the fix. Avoids update anomalies.
Denormalization
Submission.exam (also via .question.exam)
Submission stores exam FK directly so trainers can filter all submissions by exam in one table scan. Safe because exam never changes after a submission is created.
Stored vs @property
attempt_number (stored) vs score, streak (@property)
attempt_number must be checked atomically at write time to enforce the limit — computing it later would allow race conditions. score and streak are always derivable from existing rows and never filtered on.
Singleton
PlagiarismPolicy.get() → always pk=1
Trainers need to change detection thresholds at runtime without a code redeploy. A DB singleton gives a runtime-editable config row. PolicyVersion audits every change to it.
OneToOne Extension
BehaviouralFlag.submission (1:1)
Plagiarism signals are a separate concern from the core submission. Keeping them in their own table means the Submission model stays clean, and BehaviouralFlag can evolve independently. 1:1 guarantees at most one flag per submission.
unique_together
Result(submission, test_case) · ExamEnrollment(exam, student)
DB-level guarantee that application bugs can't create duplicate rows. A student can't be enrolled twice; a test case can't be scored twice per submission. Application logic enforces logic; the DB enforces invariants.
Status State Machine
pending → running → passed / failed / error
CharField with choices stores current state. Transitions are made in code. For the job pipeline: claim sets running; complete sets passed / failed. error is set by a claim that finds the job out of attempts (dead), by the sweep when a lease expires at the attempt limit, and by complete on a question with no tests. An error submission never counts as an attempt. For C++ and Java, the Celery task sets the status. CharField (not an int) because string statuses are self-documenting in queries, the admin, and logs.
Audit Log
PolicyVersion: snapshot_before / snapshot_after
Every policy change is captured as an immutable before/after pair. JSONField is used instead of FKs to a policy version table because the schema itself may grow — JSON captures whatever existed at that moment.
JSONField for Flexible Data
BehaviouralFlag.signals_triggered
The set of triggered signals varies per submission and may grow as new signals are added. JSON avoids a rigid SignalResult join table. Rule: use JSONField only for read-only, non-filterable, schema-flexible data.
Plagiarism Detection Flow
Phase 1 — Behavioural Check
Fires when exam closes (runs synchronously, before Phase 2)
O(N) — runs for all exam submissions in batch. Called synchronously inside run_exam_plagiarism_check before Phase 2 is queued.
# plagiarism/tasks.py — run_exam_plagiarism_check for sub in submissions: run_behavioural_check(sub.id) # synchronous, not .delay()
Phase 2 — TF-IDF Cross-Comparison
Fires when exam closes
O(K×N) — only high-confidence suspects compared against full class. Triggered by Django signal.
# exams/signals.py — pre_save if previous.is_active and not instance.is_active: run_exam_plagiarism_check.delay(exam.pk)

risk = 0.40×paste + 0.30×time + 0.15×tab + 0.15×surprise # if risk > 0.2 → BehaviouralFlag created # if risk ≤ 0.2 → nothing stored (noise)

HIGH3 or more signals fired
MEDIUM2 signals fired

Phase 2 — TF-IDF Cross-Comparison
A
CeleryExam closes → signal → queue per-question tasks

Django's pre_save signal detects is_active True→False. It queues one run_question_plagiarism_check per question, staggered 30 seconds apart so Celery workers don't CPU-spike simultaneously.

# exams/signals.py if previous.is_active and not instance.is_active: run_exam_plagiarism_check.delay(instance.pk) # plagiarism/tasks.py — run_exam_plagiarism_check for i, question in enumerate(exam.questions.all()): run_question_plagiarism_check.apply_async( args=[question.id], countdown=i * 30, # stagger: Q1 now, Q2 in 30s, Q3 in 60s... )
B
CeleryFilter suspects — skip question if none are HIGH confidence

Pull all students who have a HIGH-confidence BehaviouralFlag for this question. If zero suspects, the question is skipped entirely — no TF-IDF needed. This is the key cost gate.

# plagiarism/tasks.py — run_question_plagiarism_check high_risk_student_ids = set( BehaviouralFlag.objects .filter(submission__question=question, confidence='high') .values_list('submission__student_id', flat=True) ) if not high_risk_student_ids: return # ← exits here for clean classes — no compute wasted
C
CeleryNormalize all N submissions — strip comments, rename variables

Get the best submission per student (passed attempt first, else latest). Normalize all N code strings so variable names don't affect similarity. Two students writing the same algorithm with different variable names become near-identical after normalization.

# Code normalization pipeline: # 1. Strip comments (# lines for Python, // and /* */ for JS) # 2. Remove blank lines # 3. AST parse → rename user-defined names to VAR_0, VAR_1... # (builtins like print, len, range are preserved) # Before normalization: def add_numbers(first, second): result = first + second return result # After normalization: def VAR_0(VAR_1, VAR_2): VAR_3 = VAR_1 + VAR_2 return VAR_3
D
CeleryTF-IDF vectorize full corpus → cosine similarity matrix

Vectorize all N submissions at once (fit_transform). TF-IDF converts code into a weighted token vector — tokens rare in the corpus get higher weight. Cosine similarity then gives a 0–1 score for every pair in one matrix multiplication.

vectorizer = TfidfVectorizer() matrix = vectorizer.fit_transform(normalized) # N × V sparse matrix sim_matrix = cosine_similarity(matrix) # N × N dense matrix # sim_matrix[i][j] = similarity between submission i and j # 1.0 = identical after normalization, 0.0 = nothing in common
E
CeleryUpper-triangle loop — skip pairs with no suspect, flag pairs ≥ 0.80

For every (i, j) pair, skip if neither student is a HIGH-confidence suspect. This is what makes Phase 2 O(K×N) instead of O(N²). When similarity ≥ 0.80, a PlagiarismFlag is created. The key insight: a suspect may have copied from someone with clean behaviour signals — the source wouldn't appear in suspect-only comparison.

for i in range(len(all_subs)): for j in range(i + 1, len(all_subs)): a_is_suspect = all_subs[i].student_id in high_risk_student_ids b_is_suspect = all_subs[j].student_id in high_risk_student_ids if not a_is_suspect and not b_is_suspect: continue # skip — neither side flagged similarity = float(sim_matrix[i][j]) if similarity >= 0.80: PlagiarismFlag.objects.get_or_create( submission_1=all_subs[i], submission_2=all_subs[j], defaults={'similarity_score': similarity, 'flagged': True} ) notify_plagiarism_flagged(flag) # alert trainer
Why this two-phase approach — cost comparison
Approach Comparisons (200 students, 10 suspects) Problem
All-pairs TF-IDF 200×200 / 2 = 19,900 Way too slow for every exam close
Suspects-only 10×10 / 2 = 45 Misses unflagged sources (the student who was copied from)
Phase 2 (K × N) 10×200 = 2,000 Catches unflagged sources. ~10× cheaper than all-pairs.
