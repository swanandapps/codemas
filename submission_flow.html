Flow begins
1
Browser Student submits code

Student hits Submit. Browser sends a POST request with the question ID, code, and language.

// ExamTakeView.vue — frontend const res = await api.post('/submissions/', { question: questionId, code: editorCode, language: 'python', })
2
Django Validate input & fetch question

Django receives the request. Checks the question exists. Validates the serializer fields.

# submissions/views.py question = Question.objects.filter(pk=question_id).first() if not question: return Response({'error': 'Question not found'}, status=404) serializer = SubmissionCreateSerializer(data=request.data) if not serializer.is_valid(): return Response(serializer.errors, status=400)
3
Postgres Count existing attempts — enforce policy limit

Django queries Postgres to count how many submissions this student has already made for this question. The limit comes from PlagiarismPolicy — a trainer-configurable singleton. If at or over the limit, the request is rejected before any row is written.

# submissions/views.py max_attempts = PlagiarismPolicy.get().max_attempts attempt_number = Submission.objects.filter( student=request.user, question=question ).count() + 1 if attempt_number > max_attempts: return Response({'error': 'Max attempts reached'}, status=403) # e.g. student has 1 existing row → attempt_number = 2 # if max_attempts = 3, this is allowed; 4 would be rejected
4
Postgres Write submission row — status: pending

Django writes the submission to Postgres as pending. This is the permanent record. attempt_number is the value calculated from the Postgres count in step 3.

# submissions/views.py submission = serializer.save( student=request.user, exam=question.exam, attempt_number=attempt_number, ip_address=request.META.get('REMOTE_ADDR'), ) # Postgres row after this step: # id=42, status='pending', student_id=1, question_id=7, attempt_number=2
5
Django Push execution job to Celery queue via Redis LPUSH

.delay() does NOT run the function. It serializes the task name + args to JSON and does LPUSH on the Redis "celery" list. Only the execution job is pushed here — behavioural analysis runs post-exam alongside Phase 2, not per-submission.

# submissions/views.py execute_submission.delay(submission.id) # What .delay() actually does internally: # LPUSH celery '{"task":"execution.tasks.execute_submission","args":[42]}' # Redis queue after this step: # celery → [ execute(42) ]
6
Browser Receive 201 response — open SSE stream

Django immediately returns 201 with status=pending. The browser then opens an SSE (Server-Sent Events) connection to stream the result when it's ready. This is a long-lived HTTP connection — not polling.

// Browser receives: { id: 42, status: 'pending', ... } // Then immediately opens SSE stream: const es = new EventSource(`/api/submissions/42/stream?token=...`) es.onmessage = (e) => { const data = JSON.parse(e.data) if (data.status === 'passed' || data.status === 'failed') { es.close() showResult(data.status) } }
7
Redis Django subscribes to pub/sub channel for this submission

The SSE endpoint in Django subscribes to a Redis pub/sub channel named "submission:42". It then sends "waiting" to the browser and blocks — waiting for Celery to publish on that channel.

# submissions/sse.py def event_stream(): r = redis.Redis.from_url(os.environ.get('REDIS_URL')) pubsub = r.pubsub() channel = f"submission:{submission_id}" # "submission:42" pubsub.subscribe(channel) yield f"data: {json.dumps({'status': 'waiting'})}\n\n" for message in pubsub.listen(): # ← blocks here, sleeping if message['type'] == 'message': yield f"data: {message['data'].decode()}\n\n" break # one result, done pubsub.unsubscribe(channel)
Celery worker wakes up
8
Celery Worker BRPOP unblocks — worker picks up the job

The Celery worker was sleeping on BRPOP — a blocking Redis command that waits until a job arrives. The moment Django did LPUSH in step 5, Redis woke the worker up. The worker deserializes the JSON, looks up the function by name in its task registry, and calls it.

# This is inside Celery library code — not our code # celery/worker/consumer.py (simplified) while True: message = redis.BRPOP("celery", timeout=0) # blocks until job arrives task_name = message["task"] # "execution.tasks.execute_submission" fn = task_registry[task_name] # looks up @shared_task function fn(*message["args"]) # calls execute_submission(42)
9
Celery Worker Set status to running — publish to SSE stream

Worker saves "running" to Postgres, then immediately publishes to the Redis pub/sub channel. Django's SSE endpoint is already subscribed — it receives this and forwards it to the browser, so the student sees a live "Running…" indicator before execution even finishes.

# execution/tasks.py submission.status = 'running' submission.save() r = redis.Redis.from_url(os.environ.get('REDIS_URL')) r.publish(f"submission:{submission_id}", json.dumps({'status': 'running'})) # SSE stream immediately forwards to browser: # data: {"status": "running"}
10
Docker / Lambda Run student code against each test case in isolation

For each test case, a Docker container is spun up with the student's code and test input. The container has no network, 128MB memory limit, and is destroyed after running. Output is compared against expected output.

# execution/tasks.py — run_in_docker() for test_case in submission.question.test_cases.all(): output, error, exec_time = run_in_docker( code=submission.code, language=submission.language, input_data=test_case.input_data, ) passed = (output.strip() == test_case.expected_output.strip()) # Inside run_in_docker: result = client.containers.run( 'python:3.11-alpine', ['python3', '-c', wrapped_code], network_disabled=True, # no internet mem_limit='128m', # memory cap remove=True, # auto-destroy container )
11
Postgres Save Result rows, update submission status to passed/failed

One Result row is written per test case. Then the submission status is updated to passed (all tests passed) or failed.

# execution/tasks.py Result.objects.create( submission=submission, test_case=test_case, passed=passed, actual_output=output, execution_time_ms=exec_time, error_message=error, ) submission.status = 'passed' if all_passed else 'failed' submission.save() # Postgres after this step: # submissions: id=42, status='passed' # results: 3 rows (one per test case)
12
Redis Celery publishes result to pub/sub channel

Celery publishes the final status to the "submission:42" Redis channel. Any subscriber listening on that channel is immediately notified. Celery doesn't know or care who's listening.

# execution/tasks.py r = redis.Redis.from_url(os.environ.get('REDIS_URL')) channel = f"submission:{submission_id}" # "submission:42" payload = json.dumps({'status': submission.status}) r.publish(channel, payload) # Redis PUBLISH command: # PUBLISH submission:42 '{"status": "passed"}' # → Redis immediately wakes everyone subscribed to this channel
13
Django SSE endpoint forwards each status — closes only on terminal

The SSE loop unblocks each time Celery publishes. It forwards every message to the browser and only closes the stream when the status is a terminal value — passed, failed, or error. Intermediate statuses like "running" flow through and the stream stays open.

# submissions/sse.py terminal = {'passed', 'failed', 'error'} for message in pubsub.listen(): if message['type'] == 'message': payload = message['data'].decode('utf-8') yield f"data: {payload}\n\n" # forward to browser if json.loads(payload).get('status') in terminal: break # terminal — close stream pubsub.unsubscribe(channel) # Messages forwarded in order: # data: {"status": "running"} ← step 9 publish, stream stays open # data: {"status": "passed"} ← step 12 publish, stream closes
14
Browser Receive result — show passed ✓ or failed ✗

The browser EventSource fires for every message. Intermediate statuses update the UI in real-time. When a terminal status arrives, the stream is closed and the final result is shown.

// Browser — EventSource handler fires for each message es.onmessage = (e) => { const data = JSON.parse(e.data) // ① status: "waiting" → "Waiting in queue…" // ② status: "running" → "Running your code…" ← new // ③ status: "passed" → "✓ Passed" updateStatusUI(data.status) if (data.status === 'passed' || data.status === 'failed' || data.status === 'error') { es.close() // terminal — close SSE stream } }

Table Connections
From Field To Type Pattern / Why
Question .exam → Exam N → 1 Normalization — many questions per exam; exam title lives in one row
TestCase .question → Question N → 1 Normalization — expected_output belongs to the question, not every result
ExamEnrollment .exam + .student → Exam + User Junction M:N resolved — student enrolls in many exams; exam has many students
Submission .student / .question → User + Question N → 1 Core FKs — submission always belongs to one student and one question
Submission .exam → Exam N → 1 Denormalization — also reachable via .question.exam, but stored here for direct one-table filtering
Result .submission → Submission 1 → N One submission runs against N test cases → N Result rows, one per test case
Result .test_case → TestCase N → 1 Normalization — actual_output goes on Result; expected_output stays on TestCase
BehaviouralFlag .submission → Submission 1 : 1 Extension — adds plagiarism data without polluting the core Submission table
PlagiarismFlag .submission_1 / ._2 → Submission × 2 N → 1 Cross-comparison — one row per similar pair; unique_together prevents duplicate pairs
PolicyVersion .changed_by → User N → 1 Audit trail — immutable before/after snapshots of every policy change
DisputeRequest .student / .resolved_by → User × 2 N → 1 Two FKs to same table — different roles (submitter vs resolver)
Design Patterns Used
Normalization
Exam → Question → TestCase
Each piece of data lives in exactly one place. TestCase.expected_output is never duplicated — update it once and every query sees the fix. Avoids update anomalies.
Denormalization
Submission.exam (also via .question.exam)
Submission stores exam FK directly so trainers can filter all submissions by exam in one table scan. Safe because exam never changes after a submission is created.
Stored vs @property
attempt_number (stored) vs score, streak (@property)
attempt_number must be checked atomically at write time to enforce the limit — computing it later would allow race conditions. score and streak are always derivable from existing rows and never filtered on.
Singleton
PlagiarismPolicy.get() → always pk=1
Trainers need to change detection thresholds at runtime without a code redeploy. A DB singleton gives a runtime-editable config row. PolicyVersion audits every change to it.
OneToOne Extension
BehaviouralFlag.submission (1:1)
Plagiarism signals are a separate concern from the core submission. Keeping them in their own table means the Submission model stays clean, and BehaviouralFlag can evolve independently. 1:1 guarantees at most one flag per submission.
unique_together
Result(submission, test_case) · ExamEnrollment(exam, student)
DB-level guarantee that application bugs can't create duplicate rows. A student can't be enrolled twice; a test case can't be scored twice per submission. Application logic enforces logic; the DB enforces invariants.
Status State Machine
pending → running → passed / failed / error
CharField with choices stores current state. The Celery task enforces valid transitions in code. CharField (not an int) because string statuses are self-documenting in queries, the admin, and logs.
Audit Log
PolicyVersion: snapshot_before / snapshot_after
Every policy change is captured as an immutable before/after pair. JSONField is used instead of FKs to a policy version table because the schema itself may grow — JSON captures whatever existed at that moment.
JSONField for Flexible Data
BehaviouralFlag.signals_triggered
The set of triggered signals varies per submission and may grow as new signals are added. JSON avoids a rigid SignalResult join table. Rule: use JSONField only for read-only, non-filterable, schema-flexible data.
Plagiarism Detection Flow
Phase 1 — Behavioural Check
Fires when exam closes (runs synchronously, before Phase 2)
O(N) — runs for all exam submissions in batch. Called synchronously inside run_exam_plagiarism_check before Phase 2 is queued.
# plagiarism/tasks.py — run_exam_plagiarism_check for sub in submissions: run_behavioural_check(sub.id) # synchronous, not .delay()
Phase 2 — TF-IDF Cross-Comparison
Fires when exam closes
O(K×N) — only high-confidence suspects compared against full class. Triggered by Django signal.
# exams/signals.py — pre_save if previous.is_active and not instance.is_active: run_exam_plagiarism_check.delay(exam.pk)

≥ 70% pasted1.0

easy=90s · medium=240s · hard=480s

Code similarity vs previous attempt (SequenceMatcher)
<25% similar + passed1.0

Combined Risk Score + Confidence
risk = 0.40×paste + 0.30×time + 0.15×tab + 0.15×surprise # if risk > 0.2 → BehaviouralFlag created # if risk ≤ 0.2 → nothing stored (noise)
Confidence based on how many signals fired:
HIGH3 or more signals fired
MEDIUM2 signals fired
LOW1 signal fired
Only HIGH confidence students enter Phase 2 cross-comparison.
Phase 2 — TF-IDF Cross-Comparison
A
CeleryExam closes → signal → queue per-question tasks

Django's pre_save signal detects is_active True→False. It queues one run_question_plagiarism_check per question, staggered 30 seconds apart so Celery workers don't CPU-spike simultaneously.

# exams/signals.py if previous.is_active and not instance.is_active: run_exam_plagiarism_check.delay(instance.pk) # plagiarism/tasks.py — run_exam_plagiarism_check for i, question in enumerate(exam.questions.all()): run_question_plagiarism_check.apply_async( args=[question.id], countdown=i * 30, # stagger: Q1 now, Q2 in 30s, Q3 in 60s... )
B
CeleryFilter suspects — skip question if none are HIGH confidence

Pull all students who have a HIGH-confidence BehaviouralFlag for this question. If zero suspects, the question is skipped entirely — no TF-IDF needed. This is the key cost gate.

# plagiarism/tasks.py — run_question_plagiarism_check high_risk_student_ids = set( BehaviouralFlag.objects .filter(submission__question=question, confidence='high') .values_list('submission__student_id', flat=True) ) if not high_risk_student_ids: return # ← exits here for clean classes — no compute wasted
C
CeleryNormalize all N submissions — strip comments, rename variables

Get the best submission per student (passed attempt first, else latest). Normalize all N code strings so variable names don't affect similarity. Two students writing the same algorithm with different variable names become near-identical after normalization.

# Code normalization pipeline: # 1. Strip comments (# lines for Python, // and /* */ for JS) # 2. Remove blank lines # 3. AST parse → rename user-defined names to VAR_0, VAR_1... # (builtins like print, len, range are preserved) # Before normalization: def add_numbers(first, second): result = first + second return result # After normalization: def VAR_0(VAR_1, VAR_2): VAR_3 = VAR_1 + VAR_2 return VAR_3
D
CeleryTF-IDF vectorize full corpus → cosine similarity matrix

Vectorize all N submissions at once (fit_transform). TF-IDF converts code into a weighted token vector — tokens rare in the corpus get higher weight. Cosine similarity then gives a 0–1 score for every pair in one matrix multiplication.

vectorizer = TfidfVectorizer() matrix = vectorizer.fit_transform(normalized) # N × V sparse matrix sim_matrix = cosine_similarity(matrix) # N × N dense matrix # sim_matrix[i][j] = similarity between submission i and j # 1.0 = identical after normalization, 0.0 = nothing in common
E
CeleryUpper-triangle loop — skip pairs with no suspect, flag pairs ≥ 0.80

For every (i, j) pair, skip if neither student is a HIGH-confidence suspect. This is what makes Phase 2 O(K×N) instead of O(N²). When similarity ≥ 0.80, a PlagiarismFlag is created. The key insight: a suspect may have copied from someone with clean behaviour signals — the source wouldn't appear in suspect-only comparison.

for i in range(len(all_subs)): for j in range(i + 1, len(all_subs)): a_is_suspect = all_subs[i].student_id in high_risk_student_ids b_is_suspect = all_subs[j].student_id in high_risk_student_ids if not a_is_suspect and not b_is_suspect: continue # skip — neither side flagged similarity = float(sim_matrix[i][j]) if similarity >= 0.80: PlagiarismFlag.objects.get_or_create( submission_1=all_subs[i], submission_2=all_subs[j], defaults={'similarity_score': similarity, 'flagged': True} ) notify_plagiarism_flagged(flag) # alert trainer
Why this two-phase approach — cost comparison
Approach Comparisons (200 students, 10 suspects) Problem
All-pairs TF-IDF 200×200 / 2 = 19,900 Way too slow for every exam close
Suspects-only 10×10 / 2 = 45 Misses unflagged sources (the student who was copied from)
Phase 2 (K × N) 10×200 = 2,000 Catches unflagged sources. ~10× cheaper than all-pairs.
